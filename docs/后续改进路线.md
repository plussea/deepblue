# DeepBlue 后续改进路线：可恢复、可验证的 Coding Agent

整理日期：2026-09-20。

本文用于指导后续开发和实验，不表示功能已经实现，也不作为新的代码行为约定。当前状态依据本地代码与 README 核对；本文没有重新运行测试或真实模型接口，没有发布任何代码。

## 1. 项目定位与取舍

目标：让 Agent 在多轮编码任务中保留关键约束、正确处理执行中断，并用真实证据判断任务是否完成。

优先做出“可复现问题 → 针对性机制 → 对照验证”的完整成果。先沿用单 Agent 和现有 CLI，不为增加简历关键词而优先引入多 Agent、向量数据库或复杂平台。

建议主线：**完成验证 → 上下文管理 → 中断恢复**。同时建立小规模真实任务评测，为每次改进提供基线。仓库理解、代码长期质量和权限隔离作为后续方向。

## 2. 当前基础：以 v0.2 为起点

| 能力 | 当前观察 | 后续缺口 |
|---|---|---|
| Agent Loop | 模型驱动多轮工具调用，反馈工具结果和错误 | 无工具调用时返回 `completed`，不等于验收通过 |
| 工具 | read、write、edit、shell、find、grep | 缺少符号级定位和引用关系检索 |
| 编辑与命令 | 唯一匹配、Diff、临时文件替换、超时及进程树清理 | 这些机制不等于完整事务或安全沙箱 |
| 会话 | JSONL 追加记录、文件锁、未知调用不自动重放 | 恢复后仍需核对实际工作区和执行副作用 |
| 上下文 | 手动 `/compact`，保留近期轮次、原始历史和工具配对，失败保留原上下文 | 缺少自动触发、结构化状态校验和系统性质量对照 |
| 交互与用量 | 流式显示、用量记录与查看 | 缺少任务级成功成本、重复行为和无进展分析 |
| 验证材料 | README 记录 58 项本地测试及真实 API 联调 | 属于已有记录；不能等同于通用编码任务完成率 |

实现入口：`src/deepblue/agent.py`、`session.py`、`compaction.py`、`tools/`。已有验证材料见 `docs/live-integration.md`、`docs/v0.2.md`。新增模块名称在下文仅作建议。

## 3. P0：把“模型结束”与“任务验收通过”分开

### 问题

模型可能没有运行测试、遗漏需求，或在失败后直接给出总结。当前 `completed` 表示模型结束本轮对话，不能证明代码正确。

### 最小实现

1. 在任务入口支持显式验收配置，包括验证命令、执行目录和超时；从用户或评测配置获得，不自动执行仓库中不可信文件声明的命令。
2. 分开记录执行状态和验收状态，避免用一个字段混合两种语义。
3. 模型结束后，由程序执行约定检查，保存命令、退出码、日志路径及验证时的工作区版本。
4. 失败时可以把结果反馈给模型继续修复，但限制修复次数和总预算。
5. 无验收条件时输出“未验证”，不强行认定失败，也不默认通过。纯解释类任务可以记录“不适用”。

建议状态示意：

```json
{
  "execution_status": "finished",
  "verification_status": "passed",
  "verification_scope": "configured_checks",
  "evidence": [{"command": "...", "exit_code": 0, "log_path": "..."}]
}
```

`passed` 只表示指定检查通过，不代表所有需求被证明正确。检查环境不可用应标为 `blocked` 或 `error`，与断言失败区分。继续编辑后，旧的通过结果必须失效或明确标为对应旧版本。

### 验收标准

- 模型声称完成但测试失败，程序不得显示验收通过。
- 缺少测试、命令超时、依赖缺失时，有明确状态和证据。
- 修改代码后不会继续沿用修改前的通过结论。
- 修复循环受预算限制；达到上限后如实报告失败。
- 独立验收测试由外部评测器保管或以权限隔离，不能依赖提示词阻止 Agent 修改答案。

### 对照实验

比较当前结束机制与加入验证机制后的真实任务完成率、误报完成率、调用成本和耗时。额外验证会增加成本，不能只报告准确性收益。

## 4. P1：从手动摘要提升为可评测的上下文管理

### 问题

长历史中包含重复读取、过期代码及大量日志。已有摘要能减少输入，但可能遗漏约束或错误地记录验证状态。不能只根据压缩比判断质量。

### 最小实现

- 保留现有原始 JSONL，将发给模型的活动上下文与历史档案分离。
- 把摘要中的关键任务状态结构化：目标、约束、修改文件、已执行验证、未解决问题和下一步。
- 为验证状态关联实际日志；重要路径、标记和数值尽量从原记录校对，避免只相信模型摘要。
- 长工具输出外置保存，活动上下文保留结果概览与回读路径；实际错误信息不能被统一截掉。
- 增加可配置的自动压缩触发策略，避免连续反复压缩；保留近期完整消息组及工具配对。
- 大文件被修改后，对旧读取内容添加过期标记或触发重新读取。

字节数不是 Token 数。使用字节阈值时明确它只是本地保护；统计模型成本时优先使用服务返回的真实用量，并计入摘要调用。

### 验收标准

- 压缩前后保留目标、禁止事项、关键标记及真实验证结论。
- 工具调用与结果不拆散；存在未完成调用时不进行不合法压缩。
- 摘要失败或取消不破坏旧上下文；恢复会话后能重建压缩视图。
- 无法有效压缩或近期单轮仍过大时，明确停止或提示处理，不进入压缩死循环。

### 对照实验

固定模型、任务及预算，比较三组：完整历史、当前手动摘要策略、改进策略。必要时增加简单截断作为基线。

记录任务完成率、输入/输出 Token、摘要开销、关键约束保留率和重复读取次数。重复读取应区分“文件已变化后的必要重读”与“未变化内容的无效重读”。不通过故意降低基线预算制造收益。

## 5. P1：恢复会话之后核对真实执行状态

### 问题

进程可能在文件已经写入、但结果尚未记录时中断。对话日志恢复成功，不代表外部状态恢复成功。当前未知调用不自动重放是合理基础。

### 最小实现

1. 显式记录工具调用开始、完成、失败或结果未知的事件。
2. 对文件编辑记录目标路径及必要的前后哈希；恢复时核对当前内容。
3. 对 Shell 保留日志与执行信息。不能仅凭旧 PID 认定进程仍属于原任务。
4. 对未知操作先做只读检查，再决定继续、允许重试或请求用户处理。
5. 生成恢复摘要：已确认完成、结果未知、工作区外部变更以及建议下一步。

不要对任意 Shell 命令声称幂等，也不要宣称实现了 exactly-once。Git Diff 可辅助核对，但需区分用户原有修改，不能自动回滚整个工作区。

### 故障注入验收

| 中断位置 | 需要确认的行为 |
|---|---|
| 工具执行前 | 不误报执行成功 |
| 文件修改后、结果写日志前 | 能识别可能已生效，不能盲目重复写入 |
| Shell 执行中 | 明确进程和结果的不确定性，保留可用日志 |
| 会话记录写入一半 | 仅修复未提交尾部，完整记录损坏应显式报错 |
| 恢复前文件被用户修改 | 发现状态变化，避免按过期内容继续修改 |

统计注入场景中的恢复后完成率、重复副作用次数、错误成功判定和人工介入次数。必须报告场景总数与失败案例，不能只演示一次成功恢复。

## 6. P2：仓库定位与按需检索

当前已具备 `find` / `grep`，不重复开发基础文件搜索。

建议逐步增加符号定义、引用定位、精简目录/模块地图，以及从错误堆栈到函数、调用方、测试文件的关联检索。地图和索引要识别文件变更，避免继续使用过期结果。

先比较现有搜索与符号检索；确认存在语义定位缺口后再考虑向量检索。评价正确定位所需调用次数、相关文件召回及端到端修复率，同时记录索引开销。

## 7. P2：连续需求变更下的代码质量

构造对同一项目连续提出多个需求的任务，检查每轮功能与历史回归。观察重复代码、复杂度、无关改动和人工可读性，不将代码行数越少等同于质量越好。

可增加改动范围检查与结构质量反馈，但先验证其是否改善结果，避免审阅模型不停提出无关重构。若加入模型审阅，需要固定预算，并单独计算其成本。

## 8. P2：执行权限与隔离

当前工作目录不是访问权限边界。文件工具的路径限制也不能限制任意 Shell 行为。

先定义允许的文件范围、网络访问和需确认的操作；进一步用适合目标平台的隔离环境落实限制。使用一次性工作副本测试越界访问与危险操作。路径检查需考虑符号链接等绕过方式，不能依靠简单字符串前缀或命令黑名单宣称具备沙箱。

这一方向有价值，但跨平台成本较高，优先在一个明确支持的平台验证。

## 9. 共用评测方案

### 任务与运行设置

- 首批可选 20—30 个真实小型编码任务，覆盖缺陷修复、增量功能、跨文件修改和故障恢复；此数量是起步建议，不能代表广泛泛化能力。
- 每个任务保存干净起始快照、用户需求、允许修改范围、独立验收方法及环境配置。
- 调试任务与最终保留任务分开，避免反复针对相同样本调整后直接汇报其结果。
- 基线与改进版使用相同模型、解码参数、环境和预算。每次运行从独立工作副本开始，避免上次修改污染结果。
- 对关键比较进行多次独立运行；小样本至少报告成功数/总数和重复运行波动。
- 测试错误与基础设施失败分开记录，不得事后只删除不利样本。
- 真实接口会产生费用，执行前明确预算与任务范围；本路线文档本身不授权批量 API 运行。

### 指标定义

| 指标 | 口径 |
|---|---|
| 任务完成率 | 独立验收通过的任务运行数 / 全部任务运行数 |
| 误报完成率 | 声称完成但独立验收失败的运行数 / 声称完成的运行数；分母为零时记 N/A |
| 成本 | 报告全部尝试的总 Token/费用；每成功任务成本＝总尝试成本 / 成功数，成功数为零时记 N/A |
| 耗时 | 端到端耗时，包含工具、摘要、验证和重试；同时报告失败与超时数量 |
| 恢复可靠性 | 在规定故障注入场景下统计恢复后通过率、重复副作用及人工介入 |
| 压缩质量 | 关键约束保留情况、活动上下文缩减量及最终任务效果 |

同时保存模型版本、代码版本、任务 ID、运行 ID、执行状态、验收证据、用量、耗时和失败分类。日志需脱敏，不记录 API Key。

### 两层测试不可混淆

- 脚本化模型响应＋真实工具执行：验证协议、文件操作、恢复和运行时控制是否正确。
- 真实模型＋独立任务验收：衡量 Agent 实际完成任务的能力。

已有本地集成测试和 API 冒烟测试不能替代真实任务评测，但仍是开发回归的重要基础。

## 10. 推荐实施顺序与交付物

| 阶段 | 范围 | 完成后应有的材料 |
|---|---|---|
| A | 固定当前基线，建立任务配置与评测记录 | 可复现任务、运行脚本、基线结果与失败分类 |
| B | 完成状态分离与程序化验证 | 验证记录、独立验收、误报完成和成本对照 |
| C | 在现有压缩上增加状态校验和触发策略 | 压缩对照、约束遗漏案例、Token 与完成率数据 |
| D | 工作区核对及故障注入 | 中断位置矩阵、恢复结果、未知副作用处理记录 |
| E | 按主要失败原因选择检索、代码质量或隔离 | 单一问题的改进与对照，不同时堆叠多个模块 |

每个阶段先完成最小闭环，再根据失败记录决定下一步。后续实际功能开发遵循仓库 `AGENTS.md` 的 Issue 与 README 工作流程；本文仅新增规划文档，不代表实现或发布。

## 11. 对应的简历成果表达

尚未实现的机制和未测出的指标不写成已完成。完成后可以围绕以下结构压缩为三条：

- 自主执行与恢复：实现编码执行闭环，结合会话日志与工作区状态核对恢复中断任务，并通过故障注入验证。
- 上下文管理：实现结构化状态与历史压缩，在固定模型和任务集上报告 Token、完成率及约束保留的实测变化。
- 完成验证：分离模型结束与验收通过，通过独立任务测试报告完成率、误报完成率和成本。

不必承诺解决通用 Coding Agent 的所有问题；一项有失败案例、有实现、有对照的改进，比功能清单更有说服力。

## 12. 研究与工程参考

以下为前序调研使用的一手来源，用于支持问题选择，不证明 DeepBlue 已具备相应能力，也不把旧实验结果当作所有当前模型的表现。

- [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：上下文筛选、压缩和按需获取。
- [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：跨会话进展、交接材料和提前结束问题。
- [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：Agent 评测、结果验证与执行轨迹。
- [Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)：会话、执行循环和运行环境的职责分离。
- [SWE-Bench Pro](https://arxiv.org/abs/2509.16941)：复杂仓库与长流程软件工程任务。
- [SlopCodeBench](https://arxiv.org/abs/2603.24755)：持续需求变更下的结构退化和冗余问题。
- [Trustworthy agents in practice](https://www.anthropic.com/research/trustworthy-agents)：工具权限、运行环境和可信执行。
